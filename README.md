# FR3 Hybrid Planning platform

Real Franka FR3 kinematics + MoveIt 2 Hybrid Planning + MuJoCo execution, built as the experimental platform for the "Predictive Physical Realizability" paper (`../predictive_realizability_paper_draft.md`, one level up — this `ros2_ws/` tree is `.gitignore`'d from that paper repo on purpose: it's engineering infrastructure, not paper content, so it has its own git history in *this* directory).

The paper's core claim is a certificate-driven, predictive local planner (**B3**) that catches a future torque violation before it happens, versus a reactive baseline (**B2**) that only checks the current instant. This platform ports both, plus the reduced-order Python reference's Level 0-4 response hierarchy, into real MoveIt 2 Hybrid Planning C++ plugins running against MuJoCo-simulated FR3 dynamics — not a toy model.

```
                        launch files, controller config. No governor logic of its 
                        own — wires everything else together. Both the URDF and 
                        the MJCF carry a matching "payload" link/body (Phase 4b) 
                        at fr3_link8's offset, mass set at launch time from 
                        FR3_PAYLOAD_MASS_KG — see "Real bugs found and fixed" 
                        below for why BOTH models need it, not just the simulated one.
fr3_dynamics/           Shared KDL-based inverse dynamics (mass matrix,
                        Coriolis+gravity, KDL<->MoveIt joint index
                        mapping). Used by B2 and B3 so they share ONE
                        dynamics code path (paper's B2-vs-B3 fairness
                        principle) — this is load-bearing, not incidental.
                        Also has a Jacobian + FK solver and a shared
                        ForceSchedule struct (Phase 4c) for external
                        end-effector force handling (ramp or
                        position-triggered spring).
fr3_b2_local_planner/   B2: reactive baseline. Current-instant-only
                        torque-feasible qddot projection via OSQP.
fr3_b3_local_planner/   B3: predictive certificate + Level 0/1/2/4

                        code lives here.
```

## The Level 0–4 hierarchy (paper Sec. V-B, `code/local_planner.py`)

| Level | What | Where | Cadence |
|---|---|---|---|
| 0 | Pass nominal through | both plugins | — |
| 1 | Retime (slow down by λ∈[1,λ_max]) | `HorizonTrajectoryOperator` | once per new route |
| 2 | Reshape (QP over qddot) | both, route- and cycle-level | route: once/route; online: every cycle |
| 3 | Reroute (via-point candidate, caller-configured) | `HorizonTrajectoryOperator` | once per new route, only if 1 and 2 both fail |
| 4 | Sticky brake | `B3ConstraintSolver` | every cycle, once triggered, forever |

Ordering per route: **retime → reshape → reroute**, tried only if the previous one didn't fix things; reroute itself re-runs retime then reshape on the alternate candidate (sub-levels 0/1/2) before giving up. Online, per cycle: **reshape → brake**. This exactly mirrors `code/local_planner.py::plan_route` / `online_step`'s own cascade. Level 3's candidate is **caller-configured** (`b3.via_point_offset.*`, all-zero by default = no candidate = true no-op), not searched for or generated — matches the Python reference's own explicit scope ("certificate-guided selection among caller-supplied candidates, not a general replanner").

## Phase-by-phase history

- **Phase 0–1**: environment bring-up; real FR3 kinematics + MoveIt 2 planning + MuJoCo execution, no governor. Proved the base pipeline.
- **Phase 2**: B2 as a real `LocalConstraintSolverInterface` plugin (current-instant OSQP torque projection). Verified genuinely different behavior between within-limits and artificially-over-limit goals.
- **Phase 3a**: B3's certificate + Level 0/4 only. New `HorizonTrajectoryOperator` (needed because stock `SimpleSampler` only ever exposes one waypoint, not a horizon). `fr3_dynamics` extracted as a shared package so B2 and B3 don't duplicate dynamics math.
- **Phase 3b**: Level 1 (route-level retiming). New shared `torque_margin_certificate.{hpp,cpp}` (extracted `B3ConstraintSolver`'s margin math so the route-level search reuses it) + `route_retime_search.{hpp,cpp}`.
- **Phase 3c**: Level 2 (reshape), online + route-level. New `reshape_qp.{hpp,cpp}`, a much larger sparse OSQP QP than B2's single-step one (`3 × num_joints × n` variables).
- **Phase 3d**: Level 3 (reroute). New `via_point_trajectory.{hpp,cpp}` (two-segment quintic stop-and-go candidate, ported from `code/trajectory.py::ViaPointTrajectory`). Reused Level 1/2's own machinery unchanged to evaluate/fix the candidate — genuinely small new code surface for what the hierarchy diagram makes look like a big phase. Verified: the mechanism (candidate construction, margin evaluation, retime/reshape cascade on the alternate, correct fallthrough) works correctly in every trial; the *specific* via-point offsets tried (6 trials, several directions/magnitudes/joint combinations) consistently made a wrist-joint-tight test scenario worse, not better — the stop-and-go candidate's own extra peak-acceleration demand outweighed any gravity-loading benefit found, and this held even after retiming the candidate up to `lam_max`. See `fr3_b3_local_planner/config/b3_params_reroute_test.yaml`'s header for the full finding.
- **Phase 4a**: observability + metrics harness, the first slice of "port the experiment suite" (a large, multi-experiment body of work in the Python reference — split the same way Phase 3 was split into 3a–3d). Added `/diagnostics` (`diagnostic_msgs/DiagnosticArray`, no new interface package needed) published every cycle by both `B2ConstraintSolver` and `B3ConstraintSolver` — the per-cycle state that had no log line before (Level 0 pass-through is silent). New `scripts/run_experiment.py` (formalizes the manual pkill → fresh domain ID → launch → poll-ready → send-goal dance every prior phase did by hand into a reusable harness that also drives `ros2 bag record`) and `scripts/compute_metrics.py` (reads the bag via `rosbag2_py`, computes a deliberately-scoped subset of `code/metrics.py::RunMetrics`'s fields). Verified: B1 (stock)/B2/B3 all succeed on the standard within-limits goal with near-identical final error and zero interventions for B2/B3 — the direct analog of the Python reference's own Exp 1 "no regression" check. Along the way, found the real controller has a genuine steady-state joint-space tracking residual (~0.045–0.05 rad L2, confirmed stable across a 1s settle window, not a transient) that the `HybridPlanner` action's own "SUCCESS" doesn't reflect — `compute_metrics.py`'s success tolerance is set from this measured floor, not an idealized number.
- **Phase 4b**: payload sweep (Exp 2 analog). New end-effector `"payload"` body (MJCF, `fr3.xml`) + matching `"payload"` link/`payload_joint` fixed joint (URDF, `fr3_mujoco.urdf.xacro`), both at `fr3_link8`'s pose, mass threaded from one new `FR3_PAYLOAD_MASS_KG` env var into both models from the same launch-time value (see "Real bugs found and fixed" for why both are required, not just the simulated one). `run_experiment.py`/`compute_metrics.py` refactored into reusable `run_one()`/`compute()` library functions (still work as before from the CLI) plus a `"large"` goal choice, so the new `scripts/exp2_payload_sweep.py` can call them directly across many runs instead of shelling out per-cell. Verified end-to-end: **B3's certificate first triggers an online intervention at 6kg payload, 4kg before B2's own self-reported intervention at 10kg** — a genuine, monotonic "certificate lead" (`min_margin` trends 9.65 → 5.81 → 3.21 → 1.95 → 1.13 → -12.4 → -24.2 N·m as payload rises from 0 to 10kg). B1 could not be used as a comparison baseline on this goal at all — see "Known environmental gaps."
- **Phase 4c**: external end-effector force injection (Exp 3/4 analogs). `fr3_dynamics` gained a Jacobian (`computeJacobian`), an FK solver (`computeTipPosition`), and a shared `ForceSchedule` struct (`force_schedule.hpp`, ramp or position-triggered spring), threaded through every B2/B3 call site (`b2_constraint_solver.cpp`'s reactive check; `torque_margin_certificate.cpp`/`reshape_qp.cpp`/`route_retime_search.cpp`'s online AND route-level paths, gated by a new `b3.force_known_at_plan_time` flag that is the entire Exp3-vs-Exp4 code-path difference) — matches `dynamics.py::Arm.required_torque`'s own `tau - J(q)^T@F_ext` mechanism line for line. MuJoCo injection lives in `mujoco_ros2_control.cpp`'s `update()` loop, triggered by a shared one-shot `/fr3_force_injection/start` topic (`run_experiment.py`'s `run_one()` publishes it at goal-*acceptance* time, not launch time — see "Real bugs found and fixed"). **Exp3 (unanticipated ramp disturbance, `force_known_at_plan_time=false`)**: first pass done, with an apparently-positive result (B3 detects ~0.36-0.38s before ground truth, B2 never detects) that Phase 4c-fix below later found did not reproduce once the experiment's own methodology was fixed. **Exp4 (known-in-advance position-triggered contact, `force_known_at_plan_time=true`)**: blocked — see "Known environmental gaps" for the goal-execution-fragility platform issue found while designing its goal, not a Phase 4c bug.
- **Phase 4c-fix**: fixed a real experimental-validity gap an independent external review of `scripts/` found (Phase 4c's own item 10 below) — `exp2_payload_sweep.py`/`exp3_interaction_force.py` each triggered a *fresh*, randomized/unseeded OMPL plan per cell/baseline, so nothing guaranteed the paper's own "identical geometric trajectory, geometric path and time law held fixed" framing. New `fr3_replay_global_planner` package: a `GlobalPlannerInterface` plugin (`ReplayGlobalPlanner`) that deserializes and replays one captured real `moveit_msgs/MotionPlanResponse` verbatim instead of calling OMPL — selected via `FR3_GLOBAL_PLANNER_YAML`/`FR3_REPLAY_TRAJECTORY_PATH` env vars in all three launch files (both default to real, unmodified OMPL planning when unset — a true no-op, re-verified: default `small`-goal B3 run still reproduces `min_margin=9.6489` exactly). New `scripts/capture_trajectory.py` plans once via B1's own stock launch file and saves the resulting `/global_trajectory` (added to `run_one()`'s bag topics) as raw serialized bytes. **Verified deterministic**: two independent fresh replay launches of the same captured file produced byte-identical `/global_trajectory` messages and final joint positions matching to ~3e-7 rad (pure sim/control-loop noise, not planner randomness). `exp2_payload_sweep.py`/`exp3_interaction_force.py` now capture one trajectory at the start of `main()` and replay it for every cell. **Re-running both with the fix**: Exp2's finding held up essentially unchanged (`min_margin` trend 9.65 → 5.79 → 3.21 → 1.91 → 1.10 → -0.10 → -2.54 N·m over the same `[0,3,5,6,7,8,10]`kg sweep; B3 still triggers first at 6kg, B2 at 10kg, same 4kg certificate lead — though the *magnitude* at 8/10kg is now much smaller than the earlier random-OMPL run's -12.4/-24.2, since it reflects one specific fixed trajectory rather than an ensemble of different random ones). **Exp3's finding did NOT hold up on the first pass**: under the fixed, reproducible methodology (confirmed via a same-capture rerun matching the earlier run's margin trace to 5-6 significant figures), B3's online solve loop stopped at `m_phys≈2.05` N·m — still positive — just before the margin's own linear decline would cross zero (projected ≈0.09-0.1s later). Neither B2 nor B3 detected the violation in this run.
- **Phase 4c-fix, root cause + second fix**: root-caused why that window closed where it did. `LocalPlannerComponent::executeIteration()` (`moveit_hybrid_planning`'s own source) checks `getTrajectoryProgress() > 0.995` *before* every `solve()` call; B3's own progress flag is `current_duration_ >= total_duration`, a hard binary switch — the instant it flips, the component calls `succeed()`+`reset()`+`timer_->cancel()` immediately, stopping all further `solve()`/diagnostics with **no grace period** (an earlier version of this entry claimed a "~0.3s hold-at-terminal-state extension" here — that was wrong; the "hold at terminal state" behavior only fills unreached horizon steps *within* a still-active cycle, it does not extend the loop's own lifetime). So the window is bounded almost entirely by the route's own `total_duration`. Checking why THAT was so short (~0.33s) found a second, independent, pre-existing bug: both `HorizonTrajectoryOperator::addTrajectorySegment` (B3) and stock `SimpleSampler::addTrajectorySegment` (B1/B2) call `time_parametrization_.computeTimeStamps(*reference_trajectory_)` with no scaling arguments — `TimeOptimalTrajectoryGeneration::computeTimeStamps()` defaults both `max_velocity_scaling_factor`/`max_acceleration_scaling_factor` to 1.0 when omitted, and `moveit_msgs/MotionPlanResponse` (all `LocalPlannerComponent` ever sees, via its own `global_solution_subscriber_`) carries no such fields at all — so the original `MotionPlanRequest`'s own scaling was never reachable at local re-time, for ANY baseline, on ANY goal below 1.0x. Confirmed live: `"small"` (vel_scale=0.5) and `"small_slow"` (vel_scale=0.15) produced nearly identical real route durations (0.339s vs 0.325s) — `"small_slow"`'s entire "slowed down so the force ramp unfolds during real execution" premise had never actually held. Fixed by adding new `local_velocity_scaling`/`local_acceleration_scaling` node params (default 1.0, a true no-op) to both plugins, threaded into `computeTimeStamps()`, set via new `FR3_LOCAL_VEL_SCALE`/`FR3_LOCAL_ACCEL_SCALE` env vars in all three launch files. Re-verified as a true no-op by default (`min_margin=9.6489` on `small`, unchanged). The response to these new params turned out itself to be a genuinely odd, disclosed finding — see "Known environmental gaps" — but with a value from that same neutral sweep (0.02, found before ever checking detection outcomes), **Exp3's original result reproduces robustly**: B3 detects at 0.360s after force onset (T_warning = 0.7428 − 0.360 = 0.383s), confirmed via an independent same-capture rerun matching to the same 0.360s; B2 never detects. This is now real, deterministic, and re-verified twice — not the boundary-fragile artifact either the very first (pre-any-fix) or the intermediate (trajectory-only-fixed) version of this result was.

## Real bugs found and fixed along the way (worth knowing before you touch this code)

1. **macOS `@rpath` dlopen failure under `ros2 launch`** (Phase 3a). Pluginlib's `dlopen()` inside the running `component_container_mt` process couldn't resolve sibling-package `.dylib`s via `DYLD_LIBRARY_PATH`, even with a correctly-sourced overlay — affected `fr3_dynamics` AND an unrelated, pre-existing MoveIt plugin (`ReplanInvalidatedTrajectory` → `libsingle_plan_execution_plugin.dylib`, same directory). Root cause never fully nailed down (likely a `ros2 launch` composable-node-loading quirk specific to this RoboStack/macOS setup); fixed environment- independently with an explicit `@loader_path`-based `CMAKE_INSTALL_RPATH` in every affected `CMakeLists.txt`. **If you add a new package that depends on another package's shared library, you need this too** — copy the pattern from any existing `CMakeLists.txt` here (search for `CMAKE_INSTALL_RPATH`).
2. **Duplicate `declare_parameter` across plugins sharing a node.** Both `HorizonTrajectoryOperator` and `B3ConstraintSolver` load overlapping `b3.*` params into the *same* node (MoveIt loads both plugins into `local_planner_component`). Whichever initializes first (currently `HorizonTrajectoryOperator`) must declare; the other must read via `has_parameter`/`get_parameter` instead of a second `declare_parameter`, or it throws `ParameterAlreadyDeclaredException`. **Every new shared `b3.*` param needs this guard on both sides** — grep for `has_parameter("b3.dt")` for the pattern.
3. **`getStateAtDurationFromStart` writes into an already-allocated `RobotStatePtr`**, it does not allocate one. Passing a default-null pointer segfaults inside `RobotState::interpolate` (found via a macOS crash report, not guesswork).
4. **`HorizonTrajectoryOperator::addTrajectorySegment` must call `time_parametrization_.computeTimeStamps`** (like stock `SimpleSampler` does) — without it the buffered trajectory has no real duration and the local planner declares "done" almost instantly without the robot moving.
5. **The reshape QP's hard constraint only targets `|tau| ≤ tau_max - delta_tau`, not `m_safe`** (true of the Python reference too, not introduced here). Reshape reliably improves a genuine hard-constraint violation but won't always fully restore the separate `m_safe` safety buffer in one shot — this is expected, not a bug; Level 4 is the correct, always-available fallback when it doesn't.
6. **B2/B3's certificate is entirely blind to a payload added only to the MJCF** (Phase 4b). `fr3_dynamics` builds its KDL chain from the URDF (`kdl_parser`), completely independent of MuJoCo's own MJCF — adding a payload body to `fr3.xml` alone changes only the *simulated* physics, not what the certificate computes at all (confirmed via `B3_DEBUG_HORIZON`: byte-identical margins at 5kg vs. 0kg payload before the fix). Fixed by also adding a matching `"payload"` link to the URDF (`fr3_mujoco.urdf.xacro`, child of `fr3_link8` via a fixed joint) and switching B2/B3's `tip_link` config from `"fr3_link8"` to `"payload"` in all 8 relevant config YAMLs, so the mass genuinely enters the KDL chain. Re-verified after the fix: margin at step0 dropped from 9.92 (0kg) to 3.13 (5kg), confirming the certificate now sees it. **If you ever add another MJCF-only body expecting the certificate to react to it, it won't — the URDF is the only thing `fr3_dynamics` ever reads.**
7. **A leaked-daemon DDS hang during long sequential runs** (Phase 4b). `ros2 control load_controller` (used in every launch file here) auto-spawns a persistent per-`ROS_DOMAIN_ID` `ros2cli.daemon.daemonize` background process holding its own live rclpy node/DDS participant open for up to 2 hours of inactivity. Since `run_one()` picks a fresh random domain ID on every call, a long sequence of runs (e.g. a payload sweep) leaks one daemon per call; `pkill_stragglers()`'s pattern never matched them. Confirmed live: 25+ accumulated over a ~50-minute sweep and wedged the DDS transport solid (every UDP write failing, one cell hanging indefinitely with no error at all — it never even reached starting that cell's `ros2 launch`). Fixed by adding `daemonize` to `run_experiment.py`'s `PKILL_PATTERN`, so every `run_one()` call reaps all accumulated stragglers, not just its own. **Any new script that calls `run_one()` in a loop relies on this — don't bypass `pkill_stragglers()`.**
8. **`mujoco_ros2_control`'s own ROS subscriptions were never dispatched at all** (Phase 4c). `MujocoRos2Control::init()` only ever added `controller_manager_` to `cm_executor_` (its own `MultiThreadedExecutor`) — `node_` itself, the node any NEW subscription (e.g. the Phase 4c force-injection start signal) gets created on, was never spun by anything. Confirmed live: the callback simply never fired, silently leaving the SIMULATED force never applied even though B2/B3's own certificate (a separate process, correctly spun by ITS OWN container) reacted as if it had — a fully believable but wrong result if not caught. Fixed with one line, `cm_executor_->add_node(node_);`, reusing the already-running background executor thread rather than adding a new spin loop. **Any new subscription/timer added to `mujoco_ros2_control`'s own top-level node needs this — it is not spun by default.**
9. **The force-injection start trigger fired before `send_goal()`, not at goal acceptance** (Phase 4c). Publishing it right after `wait_ready()` (matching the original design) left several seconds of unpredictable global+local planning overhead for a multi-second force ramp to complete during, before any real execution ever began — confirmed live: a 0.5s ramp was already fully held by the time a single online `solve()` cycle ran. Fixed by adding an `on_accepted` hook to `send_goal()` that fires the trigger the moment the `HybridPlanner` action server accepts the goal (much closer to real execution start) — reusing `send_goal()`'s own already-active `rclpy` node rather than creating a second one (a nested `rclpy.init()` while already spinning is not safe).
10. **Three metrics/harness robustness bugs found by an independent external review of `scripts/` (Phase 4c), all confirmed real by re-reading the actual code before fixing, all fixed and re-verified against the established baseline** (`min_margin=9.6489` on the small goal, unchanged): (a) `compute_metrics.py` silently dropped any joint missing from the final `/joint_states` sample out of the L2 error sum instead of failing loudly — understates error, could produce a false `task_success`; now raises `RuntimeError` listing the missing joints. (b) `compute_metrics.py` assumed the *first* `/diagnostics` message's *first* status entry was the controller's own — fragile if any other diagnostic publisher ever appeared on the topic first; now explicitly searches every message for `"b2_constraint_solver"`/`"b3_constraint_solver"` by name. (c) `run_experiment.py`'s `run_one()` had no `try`/`finally` around the launch+bag+goal sequence — an exception inside `send_goal()` left `bag_proc`/`launch_proc` running until a *later* call's own `pkill_stragglers()` happened to clean them up; now wrapped so teardown always runs. **The same review also raised a deeper experimental-validity concern, since fixed — see item 11 below**: `exp2_payload_sweep.py` and `exp3_interaction_force.py` each independently triggered fresh (randomized, unseeded) OMPL planning per cell/baseline, so the paper's own "identical geometric trajectory, only X varies" framing for Exp2/Exp3 was not actually guaranteed by the code.
11. **Trajectory nondeterminism across `exp2_payload_sweep.py`/`exp3_interaction_force.py` cells** (Phase 4c-fix, the concern item 10 flagged but didn't yet act on). Fixed with a new `fr3_replay_global_planner/ReplayGlobalPlanner` plugin (a `GlobalPlannerInterface` implementation that deserializes and replays one captured real `moveit_msgs/MotionPlanResponse` instead of calling OMPL) plus `scripts/capture_trajectory.py` (captures that one real plan via B1's own stock launch file). Verified deterministic (two independent replay launches of the same capture: byte-identical `/global_trajectory`, final joint positions matching to ~3e-7 rad) and verified as a true no-op on the default (non-replay) path (`min_margin=9.6489` on the small goal, unchanged). **Any new sweep script that compares baselines against each other must use this same capture+replay pattern, or it inherits the same nondeterminism gap.**
12. **Local re-planning silently ignored the goal's own `max_velocity_scaling_factor`/`max_acceleration_scaling_factor`** (found while investigating why fix #11's re-run of Exp3 stopped reproducing its earlier "~0.36-0.38s lead" result — see "Phase 4c-fix, root cause + second fix" in the phase history above for the full derivation). Both stock `SimpleSampler` (B1/B2) and `HorizonTrajectoryOperator` (B3) called `computeTimeStamps()` with no scaling arguments, defaulting to full URDF joint-limit speed regardless of what the goal requested — `"small_slow"` (vel_scale=0.15) executed at essentially the same real pace as `"small"` (vel_scale=0.5), for every baseline, since Phase 3a. Fixed with new `local_velocity_scaling`/`local_acceleration_scaling` node params (default 1.0, a true no-op) on both plugins, set via `FR3_LOCAL_VEL_SCALE`/`FR3_LOCAL_ACCEL_SCALE`. With this AND fix #11 both applied, Exp3's original result reproduces robustly (B3 detects 0.360s after force onset, T_warning=0.383s, confirmed via an independent rerun; B2 never detects). **Any goal relying on a sub-1.0 `vel_scale`/`accel_scale` to genuinely slow down real execution (not just the OMPL search) needs these two env vars set explicitly — the goal's own request-level scaling alone still does nothing at the local-replanning level.**
13. **`run_experiment.py`'s `PKILL_PATTERN` was broader than it needed to be** (one of the external review's Medium-priority findings, acted on later). `pkill -9 -f` matches ANY process on the machine whose command line contains the substring, not just this project's own — confirmed live via `ps aux` during an active launch that `component_container_mt`/`robot_state_publisher` run from fully generic shared conda-env binary paths with no project-specific args, so several of the original terms (`"component_container"`, bare `"ros2 launch"`) could in principle kill an unrelated ROS 2 project's own same-named processes if one happened to be running at the same time. ## Known environmental gaps (disclosed, not hidden)

- **`mujoco_ros2_control` has a spontaneous crash window**, roughly 5–25s after launch, cause unknown (suspected GLFW/macOS window-server instability from repeated relaunches in one session — not caused by any patch here, confirmed via isolation testing). Mitigation: always poll for both the plugin-initialized log line AND the process being alive before sending a goal; don't idle between launch and verification.
- **No SCS solver in this environment** (checked directly — only `osqp`/`OsqpEigen` are present). The Python reference falls back from OSQP to SCS for the larger whole-route reshape QP; this port is OSQP-only. When OSQP can't converge on a big problem, the code reports it and falls through cleanly (matches the "retime exhausted" pattern) — it does not silently produce a wrong answer.
- **`m_safe = 2.0` N·m** (paper's own default, calibrated on a reduced-order 3-DOF arm) has never been validated as well- or poorly-calibrated at real FR3 scale. Not blocking, but flagged since Phase 3a.
- **B1 (stock ForwardTrajectory/SimpleSampler) cannot complete the "large" goal at all**, independent of payload (Phase 4b). Confirmed directly: at payload=0/3/5/7kg its joint_states show ~0.007 rad drift (sensor noise) for the *entire* 45s window — it never starts moving; at 10kg it moves substantially (1.78 rad) but still never reaches the target. ~~B2 and B3 both execute this exact goal fine at payload=0~~ — **superseded, see "Real bugs found and fixed" #16**: B3 shows the SAME "stuck, not just slow" signature at 0kg in this session's own latest Exp2 rerun (final error ~1.51 rad vs. an initial ~1.58 rad, effectively unmoved over 46s) — not yet re-checked for B2, and not yet root-caused for either. This was NOT caught by any prior phase's own verification (which only ever checked `min_margin`/intervention booleans for this goal, never `task_success`/`final_pos_error_rad` closely) — this is specific to B1's own stock local-planner pipeline on this particular goal, first surfaced in Phase 4b because it's the first time B1 was ever pointed at the large goal (Phase 4a's B1 check used the small goal). Root cause not investigated (out of scope — B1 was only needed here as a payload-sweep comparison point, not as something to fix); `exp2_payload_sweep.py` detects this case (B1 failing at the lowest payload swept) and prints a caveat instead of a misleading "certificate lead over B1" number.
- **`mujoco_ros2_control`'s macOS build needs `MUJOCO_DIR` set explicitly and `-DCMAKE_FIND_FRAMEWORK=LAST`** after any `--cmake-clean-cache` (Phase 4b, self-inflicted while adding the payload patch). Without the first, CMake can't find `find_package(mujoco)` at all; without the second, it resolves to the `mujoco.framework` bundle in the same `lib/` dir instead of the plain `.dylib` and fails to link (`ld: framework not found mujoco`). Only matters after a clean-cache rebuild of this one package — normal incremental builds are unaffected.
- **Goal-execution fragility for any single joint moved beyond ~0.13-0.15 rad from `"small"`'s own specific, previously-validated combination** (Phase 4c, found while designing Exp4's goal). **IMPORTANT: the passes below were all conducted with the `fr3.xml` position-actuator conflict bug (see "Real bugs found and fixed" #33) undiagnosed and active.** Everything found and fixed in this entry (the oscillation, the gravity-feedforward controller) is still real and still stands, but the specific torque-threshold numbers and the final "real physical/safety boundary" conclusion at the end of this entry are superseded by #33 — read that entry for the current understanding before treating anything below as the platform's actual physical limit. **Root-caused this session** (previously blocked on not having `joint_trajectory_controller`'s own source — unblocked by discovering this environment actually has network access, fetching the real upstream source via `gh api`). Two compounding causes, both confirmed with direct instrumentation, not guesswork:
  1. `HorizonTrajectoryOperator`'s (and stock `SimpleSampler`'s) progress-advancement gate uses a SINGLE aggregate distance across all 7 joints (`next_desired->distance(current_state, joint_group_) <= 0.2 rad`) to decide whether the shared target may advance. Confirmed live via a new debug log (`B3_DEBUG_PROGRESS=1`, gated the same way as `B3_DEBUG_HORIZON`): on `"large"`, `current_duration_` froze at exactly `0.32/1.83s` (17% into the route) with `dist` pinned at EXACTLY `0.2195` — just `0.0195` rad over tolerance — unchanging for the entire remainder of a 25s run. A genuine physical equilibrium (some joint's own real tracking error settles just above the threshold and never closes further), not a transient.
  2. That equilibrium is itself driven by real torque saturation on the low-budget wrist joints (`fr3_joint5/6/7`, `tau_max=12` N·m vs `87` N·m for the base joints) combined with PID gains (`fr3_ros_controllers.yaml`) copied verbatim from the real robot's own config — confirmed via `/joint_states`' own `effort` field: `fr3_joint6`'s commanded effort sat pinned at 8-10.7 N·m (58-89% of its budget) for an entire 31s run while its position never moved. Ruled out per-joint saturation alone as the full story first, though: OTHER joints (1,2,3,5,7) were ALSO stuck despite 58-91% of THEIR OWN torque budget being unused — they were being held hostage by the shared aggregate gate (item 1), not independently torque-limited themselves.
  - **Partial fix implemented and verified** (a stall-timeout fallback, `b3.progress_stall_timeout_s` param, default 1.0s): if the shared target hasn't advanced for this long, advance anyway rather than deadlocking the whole route indefinitely. Alone, this took `"large"`'s own `final_pos_error_rad` from ~1.5-1.58 rad (every prior test) down to 0.754 rad — real, but the aggregate distance now grows unboundedly instead of deadlocking, since forcing the target forward doesn't fix the underlying speed/torque mismatch. Combined with `FR3_LOCAL_VEL_SCALE=FR3_LOCAL_ACCEL_SCALE=0.3` (empirically found — NOT monotonic: 0.5x gave 0.744, 0.3x gave the best result found (**0.494 rad**), 0.1x gave 0.887, consistent with this platform's own already-documented non-monotonic TOTG response on near-degenerate paths), roughly a 3x improvement over the original stuck state. **Still does not fully converge** (`task_success` remains `False` on `"large"` even at the best combination found) — this is a genuine, disclosed, partial mitigation, not a resolution. No regression: default behavior (`b3.progress_stall_timeout_s` unset from any goal that already worked) re-verified unchanged (`min_margin=9.6489` on `small`; Exp3's own flagship result `t_detect=0.360`/`T_warning≈0.38-0.39s` unaffected, since `"small_slow"`'s own route never comes close to the 1.0s stall threshold in normal operation).
  - **Practical implication**: `"large"`-scale goals are measurably less broken now but still not reliable — any future goal design should still prefer staying close to `"small"`'s own validated joint values, or invest in a real fix (per-joint-independent progress tracking instead of one shared scalar, torque-aware time-parametrization, or retuned low-torque-joint PID gains) rather than relying on the stall-timeout/scale-tuning combination found here.
  - **Second pass, attempting a COMPLETE fix (still not fully successful, but substantial further progress + one more real root cause found).** Found and fixed a THIRD compounding cause: `HorizonTrajectoryOperator::getTrajectoryProgress()` reported "done" purely from `current_duration_ >= total_duration` (reference progress), never checking whether the REAL robot had actually arrived — confirmed live: `LocalPlannerComponent` stops calling `solve()`/commanding entirely the instant this returns `>0.995` (per its own source), and a run that had gotten to `final_pos_error_rad=0.107` (genuinely converging, no Level 4, healthy `m_phys≈10`) was then ABANDONED once reference-progress hit 100%, and the un-commanded arm DRIFTED to `0.701` with nothing left to correct it. Fixed: now also requires the real state within `WAYPOINT_RADIAN_TOLERANCE` of the route's own final waypoint before reporting done (falls back to running until `run_one()`'s own external `goal_timeout`, same as before, if real convergence never happens — no new deadlock risk). Combined with retuned PID gains for the low-torque wrist joints specifically (`fr3_joint5/6/7`: `p` cut from `250/150/50` to `50/30/10` — the REAL robot's own gains, copied from `franka_ros2`, demand far more corrective torque per unit tracking error than these joints' `12` N·m budget can supply once ANY real error has built up, confirmed via the certificate's own math: the REFERENCE trajectory's own required torque stays healthy throughout `"large"`'s whole route, `margin≈9.6-10.0` out of `12`, so the saturation is from CONTROL-LOOP overreaction to tracking error, not the route itself being dynamically infeasible) plus the same `FR3_LOCAL_VEL_SCALE=FR3_LOCAL_ACCEL_SCALE=0.3`: `final_pos_error_rad` dropped as low as **0.094** (just above the `0.06` success threshold) in one 150s run, with the underlying trajectory showing genuine, accelerating, monotonic convergence (not a plateau) for most of that time. **But run-to-run variance is real and substantial** — a second, otherwise-identical 250s run landed at `0.182` instead of continuing to improve; this is genuine sim/timing-dependent physics jitter, not a logic bug (re-verified: `open_loop_control: true` and reducing the BASE joints' own gains too were BOTH tried and made things WORSE, ruled out as further fixes). **Still not a guaranteed, reliable fix** — `task_success=True` was not achieved in any run, though several came close. No regression from either the gain retune or the progress-signal fix (both unconditional, affecting every B3 run): re-verified `small`'s `min_margin=9.6489` and Exp3's own `t_detect=0.342`/`T_warning≈0.40s` unchanged, and re-ran the FULL Exp2 sweep — numbers reproduce within ordinary noise (e.g. `min_margin` at 5kg: `3.046→3.045`), qualitative finding (4kg certificate lead) fully intact, since Exp2's own fixed 45s per-cell timeout never gets anywhere near real convergence on `"large"` either way, before or after this fix.
  - **Third pass: characterized the variance statistically, then root-caused the oscillation the user directly observed live ("the robot oscillated very much") — the real remaining blocker, distinct from everything found in the first two passes.** Statistical characterization (README's own previously-open option) first: 8 fresh repeated trials at the then-current best config gave `final_pos_error_rad ∈ [0.1219, 0.1819]`, mean `0.1512`, `0/8` task_success — tighter and more consistently unsuccessful than the earlier 2-sample anecdote suggested, i.e. a real plateau, not noise around the `0.06` threshold. Investigating why led to directly analyzing `/joint_states` bag data: every joint shows thousands of local sign-changes in tracking error over a single ~200s run (4105-8662/joint, roughly an 11-26Hz oscillation) — a genuine sustained limit-cycle/chatter, not slow noisy convergence, fully confirming the user's live observation and explaining why the error plateaus instead of continuing to shrink. Root-causing this took several ruled-out hypotheses, each checked against real data before moving on (this platform's standing practice):
    1. *Stale horizon velocity* (fixed, see "Real bugs found and fixed" #27a) — real bug, but a full-length rerun after the fix showed unchanged extrema counts, so it wasn't (solely) the cause.
    2. *Certificate Level 0/2/4 flip-flopping* — ruled out directly: `/diagnostics` showed `level="0"` (pass-through, no reshape/brake) for all 10,049 cycles of a 200s run, `m_phys` staying healthy (9.65-10.0 vs `m_safe=2.0`) throughout.
    3. *Jaggedness already present in the raw OMPL plan* — ruled out: `/global_trajectory`'s own 13-waypoint geometric path is monotonic per joint.
    4. *Single-point-per-cycle republishing causing spline discontinuities* — ruled out by a controlled rate experiment: dropping `local_planning_frequency`/`b3.dt` 5x (50→10Hz, via a temporary `FR3_B3_PARAMS_YAML` override) did NOT proportionally cut the oscillation frequency; extrema/sec stayed tightly clustered around ~19-20/joint/sec at 10Hz vs. a *wider* 22.5-52.9/sec spread at 50Hz — the opposite of what a republish-driven-discontinuity theory predicts.
    5. **Actual root cause, confirmed decisively**: added `/fr3_arm_controller/joint_trajectory` and `/fr3_arm_controller/controller_state` to `run_experiment.py`'s recorded topics (previously unrecorded — no visibility into the real commanded/controller-internal state existed before this). The COMMANDED stream itself is smooth (joint2: 119 position extrema over 61s, ≈2/sec, essentially monotonic; inter-message timing tight, mean 20.0ms/std 1.4ms, no dropped cycles) — ruling out the planning/publishing side entirely. But `controller_state.output.effort` (the PID's own computed torque demand, before hardware clamping) is at or beyond the REAL joint torque limit **42-60% of the time, on every one of the 7 joints** (not just the retuned wrist ones), peaking at 2.7-3x over budget (e.g. joint4: demands up to 273 N·m against an 87 N·m limit; mean |effort| sits right at the limit, 83-84/87 and 11-13/12 N·m) — i.e. saturation is the NORMAL operating condition through most of the run, not an edge case. This is a classic actuator-saturation relay/bang-bang oscillation: the PID continuously demands more torque than the real hardware (`mujoco_system.cpp`'s own `joint_limits.max_effort` clamp) can deliver, the resulting under-actuated motion re-opens the tracking error, and the next cycle saturates again. Crucially, B3's OWN torque-margin certificate (`m_phys`/`m_phys_observed`) never sees this: `m_phys_observed` — which does use real measured position/velocity, per "Real bugs found and fixed" #17/#25a — stayed at `9.65-10.0` (never below `4.0`, let alone `m_safe=2.0`) for the entire oscillating run, because it evaluates the REFERENCE trajectory's own idealized `qddot` at the real state, not what the real closed-loop PID actually ends up commanding once tracking error and gain interact — a genuine blind spot in the certificate's own scope, not a bug in it.
    6. **Gain retuning tested as a candidate fix and found to help, modestly, but not resolve it** — see "Real bugs found and fixed" #27b for the matched-trial numbers. P:300 (now the repo default) is a real, verified local optimum: further reduction (P:150) reverses the improvement (too weak to track, worse `final_pos_error_rad`) without meaningfully cutting the extrema rate further.
  - **Real fix still needed — TWO candidate approaches attempted (fourth pass), both confirmed structurally incapable of resolving this, with concrete evidence, not just untried:**
    1. *Torque-aware retiming, targeting the idealized reference's own torque margin*: implemented properly (new `searchRetimeLambdaRelative`/`computeMPhysOverTrajectory`'s relative-margin output, a per-joint-budget-fraction target rather than the online safety net's tiny absolute `m_safe`, since a single absolute N·m margin can't meaningfully bound both 87 N·m base joints and 12 N·m wrist joints at once). Live-verified: on `"large"` at the current speed, EVERY joint's idealized reference demand already stays under 50% of its own `tau_max` (the new pass never triggers at its default `b3.pretrack_relative_margin=0.5`) — and pushing the target to a deliberately extreme `0.95` still can't get past `0.834` even at the maximum allowed 4x slowdown (`lam_max=4.0`), confirmed via `B3_DEBUG_HORIZON` logs. Physical reason: `tau = M(q)*qddot + C(q,qdot)*qdot + g(q)` — retiming scales the inertial (`qddot`, as `1/lambda^2`) and Coriolis (`qdot`, as `1/lambda`) terms down, but gravity `g(q)` depends only on POSITION, which retiming never changes at all. There is a hard, unavoidable floor on how much margin retiming can ever buy, and the idealized reference is already well clear of it — meaning the REAL saturation (42-60% of cycles) is not being driven by anything an idealized-reference-torque-margin check can see or fix via retiming, at any target.
    2. *Feedforward torque, to give the closed-loop PID a head start instead of sourcing 100% of required torque (including gravity) from tracking error alone*: found to be blocked by the platform itself, not just unimplemented. Confirmed directly against the exact installed `joint_trajectory_controller` version (`2.53.1`, fetched and read from the matching upstream tag): it explicitly REJECTS any trajectory message with a populated `.effort` field (`"Trajectories with effort fields are currently not supported."`, `validate_trajectory()` returns `false`) — so publishing a per-cycle `M(q)*qddot_ref + bias` feedforward torque via `/fr3_arm_controller/joint_trajectory`, the natural place to inject it given `B3ConstraintSolver` already computes `M`/`bias` for the certificate, is not possible at all with this controller. Also confirmed `mujoco_system.cpp` does no gravity compensation of its own (grepped directly, no hits) — the controller's own effort output must supply 100% of gravity-holding torque via feedback alone, unconditionally. The controller's only built-in feedforward-like knob, `gains.<joint>.ff_velocity_scale` (a fixed per-joint scalar times DESIRED VELOCITY, added directly into the effort output), was tried (both the nested and the deprecated-flat parameter forms) but never actually loaded (`joint_trajectory_controller`'s own warning about the param not being found under the expected structure persisted in both attempts, a real but un-root-caused parameter-loading quirk in this exact version) — not pursued further because, even working, it's velocity-proportional only and structurally cannot address gravity torque (nonzero even at zero velocity, position-dependent) — the same dominant term retiming already proved it can't touch either.
    - **What would actually work, per this analysis**: a custom `ros2_control` controller (replacing or wrapping `joint_trajectory_controller`) that computes true `M(q)*qddot_ref + C(q,qdot)*qdot_ref + g(q)` feedforward each cycle from the existing `fr3_dynamics` model and adds it directly to the effort output, addressing gravity (the actually-dominant term) rather than working around a controller interface that structurally can't carry it. A genuinely bigger undertaking than anything tried across all four passes so far — a new package/plugin, not a config or existing-file change. **Built in the fifth pass — see "Real bugs found and fixed" #29 for the full writeup.**
  - **Fifth pass, summary (full detail in "Real bugs found and fixed" #29): built `fr3_gravity_ff_controller`, the custom controller the fourth pass concluded was needed — genuinely eliminates the oscillation.** Gravity+Coriolis feedforward alone took extrema/sec from 22.5-57.1 down to 0-0.45 (confirmed on both 60s and 200s runs) — the first mechanism across all five passes to actually stop the oscillation, not just reduce or reshape it. Revealed a real, separate, previously-masked limitation: pure PD (`i:0`, unchanged from the stock controller) has no way to close steady-state error under any constant disturbance, so `final_pos_error_rad` plateaued (0.83-0.89, worse than #27's 0.246-0.261, since the old oscillatory chatter apparently helped progress along by accident despite never converging). Added a real integral term (with anti-windup) — genuine partial improvement (`final_pos_error_rad` 0.829→0.746), but two SEPARATE, clearly-diagnosed limits remain: base joints (1-4) are torque-saturated by `p*residual_error` alone at this gain, independent of feedforward or integral; joint7 stays almost completely frozen even with ample torque headroom (7 of 12 N·m used), ruling out "insufficient torque." No regression on `"small"` with the final (feedforward+integral) config. Opt-in via `FR3_ARM_CONTROLLER_YAML=fr3_ros_controllers_gravity_ff.yaml` (default unset = stock controller, unchanged) — recommended going forward, not yet the default, since `"large"`'s own `task_success` still isn't reached.
  - **Sixth pass, summary (full detail in "Real bugs found and fixed" #30): root-caused joint7's stall directly in MuJoCo, bypassing the ROS2 stack entirely.** Self-collision (the fifth pass's leading hypothesis) is ruled out — zero contacts at the stall pose. Coulomb friction is also ruled out — stripping it from the model entirely gave an identical result. Confirmed instead: a real, sharp torque threshold between 12 N·m (joint7's entire real budget — moves it under 0.007 rad, then hard-stops) and 20 N·m (moves the full 3+ rad range cleanly), reproducible by driving `qfrc_applied` directly with the rest of the arm held near its actual pose. Likely mechanism (not fully isolated): the model's default `damping=0.21`, inherited by joint7, combined with inertial coupling to the rest of the arm. **This is real physics in the shipped MJCF model, not a controller bug — no controller (this one, the stock PD, or a hypothetical MPC, which was also assessed and found to have no collision/contact model either) can move joint7 through this pose within its real torque budget.**
- ~~`exp2_payload_sweep.py`/`exp3_interaction_force.py` do not currently guarantee an identical geometric trajectory across cells`~~ — **fixed, Phase 4c-fix** (see "Real bugs found and fixed" #11). Separately, ~~`ground_truth.py`'s "ground truth"~~ `nominal_route_crossing.py`'s own crossing time (renamed, see "Real bugs found and fixed" #22) is still B3's own certificate model re-evaluated offline, not independent physics — this matches the Python reference's own `ground_truth_failure_time`/`Certificate.ground_truth_violation` methodology exactly (confirmed by re-reading it), so it's a faithful port, not a shortcut introduced here, but the paper should describe it as a model-consistent reference rather than an independent validation.
- ~~Exp3's online detection window is boundary-sensitive~~ — **root-caused and fixed, Phase 4c-fix** (see "Real bugs found and fixed" #12). The window itself is still bounded by the route's own `total_duration` (`LocalPlannerComponent` stops calling `solve()` the instant `getTrajectoryProgress()` flips, no grace period) — that part was always correct, just mischaracterized in an earlier version of this entry as a "~0.3s hold-at-terminal-state extension," which was wrong.
- **`TimeOptimalTrajectoryGeneration::computeTimeStamps()`'s response to `max_velocity_scaling_factor`/`max_acceleration_scaling_factor` is non-monotonic on `"small_slow"`'s own 2-waypoint path** (found while calibrating fix #12 above). An empirical sweep (`0.02` step size details in `exp3_interaction_force.py`'s own `FORCE_ENV` comment) found real route duration stays essentially flat (~0.32-0.34s) from scale 1.0 down to 0.05, then jumps abruptly to 0.61s at scale 0.02 — not the smooth, roughly-`1/scale`-ish physical response a velocity/acceleration-limited time-optimal parametrization should give. Suspected cause: the raw OMPL response for this goal is always exactly 2 waypoints (start+goal, `time_from_start=0` for both — confirmed by inspecting a captured `/global_trajectory` directly), a near-degenerate input for TOTG's own path-following algorithm; never investigated further (would need reading `time_optimal_trajectory_generation.cpp`'s own internals, a MoveIt-core third-party algorithm, not something this platform's own code controls). `exp3_interaction_force.py` uses `0.02` (the smallest value tried in that neutral, detection-outcome-blind sweep), not a value tuned against Exp3's own result. **Any future use of `FR3_LOCAL_VEL_SCALE`/`FR3_LOCAL_ACCEL_SCALE` on a different goal should re-sweep rather than assume a linear response.**

```bash
# Activate environment (RoboStack ROS 2 Humble in a conda env)
source /opt/homebrew/Caskroom/miniconda/base/etc/profile.d/conda.sh
conda activate ros_env
cd /Users/yycao/ai_learn/replan/ros2_ws

colcon build --packages-select fr3_dynamics fr3_b2_local_planner \
  fr3_b3_local_planner fr3_replay_global_planner fr3_mujoco_bringup \

# Poll for readiness before sending a goal (see "known gaps" above):
```

Test-config env vars (both launch files support these, default to the real values):
- `FR3_B2_TORQUE_LIMITS_YAML` — e.g. `config/b2_torque_limits_test_low.yaml`
- `FR3_B3_PARAMS_YAML` — e.g. `config/b3_params_test_low.yaml`, `config/b3_params_retime_test.yaml`, `config/b3_params_reshape_test.yaml`, `config/b3_params_reroute_test.yaml` (see `fr3_b3_local_planner/config/` for what each exercises)
- `FR3_PAYLOAD_MASS_KG` — end-effector payload in kg (Phase 4b), all three launch files support it, default `"0.0"`. Sets both the URDF and the MJCF's `"payload"` body/link so B2/B3's certificate and MuJoCo's simulated physics agree.
- `FR3_FORCE_MODE` (`""`/`"ramp"`/`"spring"`), `FR3_FORCE_T_ONSET`, `FR3_FORCE_RAMP_DURATION`, `FR3_FORCE_FX/FY/FZ`, `FR3_FORCE_CONTACT_Z`, `FR3_FORCE_K_CONTACT` (Phase 4c) — external end-effector force schedule, all three launch files support it, default disabled (`""`). - `FR3_GLOBAL_PLANNER_YAML`/`FR3_REPLAY_TRAJECTORY_PATH` (Phase 4c-fix) — all three launch files support it, default real unmodified OMPL planning (`config/hybrid_planning/global_planner.yaml`, `FR3_REPLAY_TRAJECTORY_PATH` unset).
